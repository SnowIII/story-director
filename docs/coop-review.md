# Coop 审核复核与修复

复核日期：2026-10-26。代码基线：`99146c6`（0.39.5）。原有 128 项测试全部通过；以下判断另用回归测试验证。

## 四个主要问题

| 审核要点 | 判断 | 本次处理 |
| --- | --- | --- |
| 保存成功后发布旧状态 | 成立。保存等待期间，来源编辑、删除、切换回复均可能使预先计算的状态失效。 | 保存前仍校验文档，确认后按实时来源重新投影，再发布和广播。增加加载代次，阻止重新加载前的旧请求覆盖当前状态或错误信息。 |
| 重设事件可覆盖已演内容 | 成立。只保留问题不能保证阶段及轮数兼容。 | 已有演出记录后冻结标题、场景、矛盾、目标、开场及轮数；问题提出后再冻结困境和问题。尚未演出的收束可修改，已有回答及路线保留。设计请求传入原计划，并拒绝事件版本已改变的迟到结果。 |
| 日志依赖过粗 | 有条件成立，已复现。25 点起步，先加 2 再加 5，切换 Coop 后启动事件；撤销早期 2 点后仍有 30 点，旧签名却会连带撤销门槛及事件。 | 新操作记录 Rank、关系、Gate、有效历史 ID 和目标事件依赖，不再依赖精确好感总数及其他事件的版本；来源和状态机校验继续执行。剩余分数低于门槛时仍撤销事件。旧日志缺少细粒度依赖时，继续使用原有保守校验，不猜测迁移。 |
| 后续输入覆盖正式回答 | 部分成立。覆盖首次回答会丢失收束依据，但保留已选路线并继续聊天本身是已有玩法，不能把每条新消息都当作改选。 | 增加 `initialAnswerSource` 保存首次回答；保留原 `answerSource` 表示最新输入，以兼容旧日志。提示词、归档及证据校验同时考虑两者。Rank 3 的选择证据仍绑定面板确认时的回答。 |

路线冲突采用明确的回报分支：模型用 `routeConflict:true` 提议重新确认，同时引用最新用户原文 `userEvidence` 和实际正文 `evidence`。程序校验事件版本、双方来源和证据后，清除本次事件的待定路线、转入 `waiting_route`；不会升阶或解除锁。用户必须在面板重新确认才能收束。普通补充继续保留路线，补归档也遵守同一规则。

程序不能仅靠文本引用判定自然语言中的全部意图；是否构成路线冲突仍需要模型按契约报告。此次修改保证有效冲突回报会触发程序状态转换，不能保证模型始终正确识别用户意图。

## 其余建议

- 拆分 `CoopRuntime`、细分宿主适配器属于结构改进建议，没有单独证明行为错误，本次不做大范围重构。
- 异步任务有效性检查合理。本次补齐保存的加载代次和重设的事件版本；现有生成取消、聊天作用域及来源校验继续保留。
- 区分事实与推断是合理原则。现有程序校验消息来源和原文证据，但引用匹配不能证明摘要、成长与冲突判断的语义必然正确。
- 长期摘要压缩可作为后续功能。当前只有四阶，已有完整历史与显式容量上限；本次不引入新的模型压缩流程。
- 诊断建议合理，但当前设置页已经展示来源失效、依赖失效及其他无效回报的数量。操作依赖明细和因果图可以后续增加。
