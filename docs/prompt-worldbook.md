# 提示词清单与世界书自定义

故事导演的提示词分给三个读者：**故事神谕**负责设计，**正文模型**负责按当前计划演出，**MVU 变量模型**负责更新数值和落拍字段。Coop 的事件回报由正文模型直接交给导演，不经过额外变量模型。

世界书 **「故事导演」** 中有 18 个独立提示词条目，原有 5 个 Coop 设计条目继续使用。每条独立判断开关：**开启且内容非空时使用世界书内容；关闭、缺失或留空时使用对应的内置默认值**。

**0.42.2 起，程序只固定读取和展示必需的结构。** XML 标签、顶层字段名、编号列表以及程序指定的数量由代码提供；字段内部的情节、文风、叙事结构和表达方式由自定义规则决定。例如篇章仍使用 `<StoryEpic>` 和「标题、篇章、章内容、大高潮、伏笔、既成事实」，但章内容可以按人物线、合作任务或其他方式组织，不必使用默认的起承转合与不同舞台。标题字数、矛盾公式、伏笔数量等均属于可替换的默认创作建议。

## 怎么修改

1. 打开酒馆世界书「故事导演」，找到对应标签的条目。
2. 编辑内容，保留条目名中的方括号标签，开启条目并保存。
3. 下一次设计或正文生成会重新读取。关闭条目即可恢复内置规则。

这些条目保持默认的 **非恒定、无关键词** 触发方式，由插件按用途读取，不需要设置关键词或把它们设为常驻。设计规则只发给对应设计任务，不随每轮正文重复发送整本世界书。

共用规则条目中放的是对应默认规则全文。任务规则和动态正文引导的条目默认放 **`{{sd.default}}`**，它只展开为当次默认的**可编辑规则部分，不包含必要返回格式**。不是固定抄录一份第一章的提示词，因此检查篇章、重排剩余拍等任务仍会得到各自正确的规则。Coop 核对归档同样将规则与 JSON 格式分开。

例如，想在内置章节规则上增加偏好，可以把 `[sd_prompt_chapter]` 改成：

```text
{{sd.default}}

本次额外创作偏好：优先使用共同实践、协商和具体成果推进人物关系。
```

若想**替换**默认创作规则，删掉 `{{sd.default}}`，直接写自己的内容：

```text
你是当前章节的剧情设计师。依据本次提供的真实历史和章表，
用人物的实际目的组织因果；优先写合作、发现与承担责任，
让不同立场都有合理行动，不反复安排同一种救援结构。
```

程序会独立补上当次任务类型、数量、已演内容保护和必要返回结构；保留 `{{sd.default}}` 也不会把结构移入可编辑部分。任务条目不引用默认规则时，七组共用设计规则及默认字段写法不会强行追加；要只微调某一层，直接编辑对应共用规则条目即可。旧自定义全文中的本任务 XML 标签会转换为字段内容要求，保留其中的写作意图，最终输出仍使用程序提供的结构；不修改世界书中保存的原文。

例如，把 `[sd_prompt_epic]` 替换为下面的内容，章表仍可正常显示在篇章面板：

```text
设计一部轻松的共同旅行故事。标题取自人物的口头禅。
每章按「行动、收获、遗留问题」组织，可以连续发生在同一地点。
大高潮采用一次安静的共同决定，伏笔只记已经出现的细节。
```

字段可以写多行，并包含「动机：」「行动：」「收获：」等自定义小标题；解析只在当前任务的已知顶层字段处切换。保留顶层字段名，避免在字段内部另起一行复用同名字段。章内容和拍继续用从 1 开始的连续编号列表，单条内容可包含分号。实际章数、拍数与局部重排范围仍使用插件设置；已有保存长度与列表上限继续适用。

## 固定返回格式清单

下面均由程序提供，不放进自定义条目：

| 任务 | 固定格式 | 必需的结构说明 |
|---|---|---|
| 篇章 | `<StoryEpic>…</StoryEpic>` | 标题、篇章、章内容（编号列表）、大高潮、伏笔、既成事实；章末检查另有 `检查:` 结论行 |
| 主线章节 | `<StoryChapters>…</StoryChapters>` | 章标题、篇章、范围、章目标、拍（编号列表）；程序按实际任务填写剩余拍数，旧返回的“分卷”也兼容 |
| 间章 | `<StoryInterludeChapter>…</StoryInterludeChapter>` | 标题、场合、拍（编号列表） |
| 支线 | `<StoryThreads>…</StoryThreads>` | 标题、目标、切入、落点、时限 |
| 插曲 | `<StoryInterlude>…</StoryInterlude>` | 标题、内容、接在（拍号或随时） |
| Coop 事件设计 | 单个合法 JSON 对象 | `targetRank`、`rounds`、情节字符串、`seeds` 四字段、`usedHistory`、`references`、`conflicts`；目标阶级、轮数、种子和历史由程序提供 |
| Coop 核对归档 | 单个合法 JSON 对象 | 未完成为 `ready:false`；完成为 `ready:true`、`evidence`、`completion`，并含 `scene` 的布尔值、数组和原文证据；路线冲突使用单独分支 |
| 正文自检与回报 | `<故事导演自检>`、`<CoopReport>` | 当前拍、自检结论，或本轮 nonce、事件／角色 ID、阶段、证据和归档数据；由各自专用契约填写 |
| MVU 数值更新 | `<UpdateVariable>` 内的 JSONPatch 或 `_.set` | 实际角色路径、0～100 整数好感与布尔锁定；正文与额外变量模型按现有分工回填 |

固定部分中的括号文字只是内容占位，不要求模型照抄，也不规定情节公式。Coop JSON 的字符串同样填写实际内容；Rank、轮数、历史 ID、已确认设定及现场收束证据仍由程序校验。模型仍可能输出不合格结构；本功能不为格式增加一次自动模型请求。

设计类条目还可以使用 `{{sd.beatTarget}}`、`{{sd.interludeBeats}}`、`{{sd.chaptersPerEpic}}`、`{{sd.intensity}}`、`{{sd.tone}}`。局部重排可用 `{{sd.keep}}`、`{{sd.remaining}}`；篇章任务可用 `{{sd.epicMode}}`。后面三个只在对应任务有意义。`{{user}}`、`{{char}}` 等酒馆宏保持原样；不认识的宏不会执行成代码。

原有 `[coop_design]` 和阶级流程继续支持 `{{coop.rankCount}}`、`{{coop.relationshipRank}}`、`{{coop.thresholds}}`，含义和开关行为保持原样。开启新的成长条目时，也会替换未编辑的旧 Coop 通用模板中相同的默认成长段落。

## 程序仍负责什么

以下内容属于运行数据或读写协议，不能靠改提示词改写进度：

- `buildUserPrompt`、`collectContextBlocks` 组装的角色卡、激活世界书、近期对话、当前章表、已演拍和真实归档。
- `renderMainSection`、`renderThreadsSection`、`renderInterludeSection`、`renderInterludeChapterSection` 中当前实际要演的内容、顺序与进度。
- `<StoryEpic>`、`<StoryChapters>`、`<StoryInterludeChapter>`、`<StoryThreads>`、`<StoryInterlude>` 的必要返回字段。
- MVU 的命名空间、路径、0～100 上限、门槛锁定、当前角色名单和当前实际值；Coop 的证据、事件 ID、阶段、路线确认、JSON 格式及现场收束检查。
- 自检标签、落拍字段及由谁回填的分工。审查执行建议可编辑，标签和状态机处理方式继续由代码决定。

Coop 当前阶段、真实用户选择、场景队列及直接回报契约来自 `coop/prompts.js`；它们与可编辑的成长和计分建议共同组成每轮提示。新功能不增加神谕或正文 API 调用，也不会为读取世界书请求额外模型。

## 更新与生效范围

自动升级会增加缺失的条目，保留用户自定义文本与开关；未编辑的默认文本随版本更新。原有 Coop 模板的保留行为不变。手动重装世界书会恢复默认内容。

设计类修改在下一次设计或「重设未演部分」时生效，已生成计划和历史归档不会被追溯改写。演出、计分和成长规则在下一次正文准备时读取；保存世界书设置也会刷新已有注入缓存。已有完整归档回报继续直接采用，不因自定义归档提示词多发一次核对请求。
